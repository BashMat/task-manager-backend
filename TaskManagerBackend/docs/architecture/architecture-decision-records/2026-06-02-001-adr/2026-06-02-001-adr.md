## Abstract

This `ADR` covers structure of `ADR` documents and rules around their usage.

> 📜 **Summary**
>
> `Architecture Decision Records (ADR)` provide context and reasons behind certain decisions. To manage this project 
> in an effective way, `ADRs` are used to document a stream of decisions. Some of them may be `Active`, while others 
> may be `Inactive` due to being replaced by other documents or related area on interest being removed entirely. 
> Other statuses also may be used.
> 
> To have clear structure and improve data processing around `ADRs`, they are designed with following considerations:
> 
> - Each `ADR` follows specific structure regarding headers and content, which makes information easy to navigate.
> - Each `ADR` acts as a snapshot of current version of `ADR`. Edits are allowed to fix typos, improve wording, text 
> and format, add missing information, update `ADR` status, etc. However, such changes must be made carefully.
> - Each `ADR` has attached metadata like identifiers, tags, etc. Such metadata files may be used via technical 
> means like scripts and other utilities.

## Introduction

A lot of decisions happen implicitly and affect work and projects. In some cases these decisions are taken
due to taste (e.g. code style or naming project, feature or task), while in other cases actual quality, performance, 
maintenance and other factors determine accepted decisions. Even when decision has serious reasons, they may be missed 
and forgotten, which later makes changes dangerous: unknown factors that were previously taken into account but 
missed during changes may later cause unexpected results, like errors or inconveniences.

`Architecture Decision Records (ADRs)` are meant to prevent such situations. Therefore, this document formalizes 
`ADR` usage for better project work.

## Decisions

### ADR structure

#### Content

1. `ADRs` MUST consist of at least two files: metadata file and actual contents file that describes actual 
decisions. `ADRs` SHOULD use uniform file format, however no requirement is currently put due to possible
changes in future regarding choice of presentation. `ADRs` MAY use `.json` files for metadata and `.md` files for 
actual content.
2. `ADRs` MUST provide following data via metadata file:
   - `id` – `UUIDv7` [(see RFC 9562)](https://www.rfc-editor.org/rfc/rfc9562) value used to identify `ADR` in uniform 
   way.
   - `code` – `string` value in format `{date}-{order}-{short-title}`, where:
     - `{date}` equals `date` value from this list.
     - `{order}` equals `order` value from this list.
     - `{short-title}` may be equal to `title` value from this list or represent its shortened version if title is too long.
     `{short-title}` MUST be used in kebab style (lowercase, hyphen separated), i.e. `short-title`.
   - `title` – `string` value with actual `ADR` title.
   - `author` – array of `string` values identifying `ADR` authors. Full names, email addresses or usernames 
   may be used, this standard does not require specific authorship format.
   - `date` – `string` value representing ISO 8601 date without time.
   - `order` – positive integer value that represents order of `ADR`. The first `ADR` uses `1`, while following `ADRs`
   use increasing values of `2`, `3`, etc. 
   - `status` – `string` value that MUST be equal to one of allowed values:
     - `Active` MUST be used for currently active decisions that are actively enforced or used in project.
     - `Inactive` MUST be used for currently inactive decisions that are not enforced in project.
   - `references` – array of references
   - `tags` – array of `string` values providing keywords for `ADR` navigation. Following values may be used 
   as example: `docs` or `documentation` for `ADRs` related to documentation; `C#` or `ASP.NET Core` related to 
   usages of actual programming language or libraries and frameworks; `API` or `Domain-Driven Design` related to 
   design decisions around specific topics.

   Use this `JSON` object from current `ADR` metadata file `2026-06-02-001-adr.json` as example:

    ```json
    {
      "id": "019e89dc-77d1-7111-b76e-34dc3e23eb57",
      "code": "2026-06-02-001-adr",
      "title": "Architecture Decision Records (ADRs)",
      "authors": [ "bashmat" ],
      "date": "2026-06-02",
      "order": 1,
      "status": "Active",
      "references": [],
      "tags": [
        "docs",
        "documentation",
        "architecture",
        "adr",
        "architecture-decision-record"
      ]
    }
    ```
3. `ADRs` content files MUST provide following:
   - Top level header with title in a form `ADR {date}-{order}: {title}`.
   - Second level headers:
     - `Document` – contains a list of values from metadata file used for fast document recognition.
     Following values are used:
       - `id`;
       - `title`;
       - `code`;
       - `date`;
       - `order`;
       - `status`;
       - `authors`.
     - `Status` – contains text explanation of `status` value with more details regarding current status. 
     For example, information on when or why document was set to `Inactive`.
     - `References` – contains representation of `references` value with possibly more details.
     - `Tags` – contains values of `tags` value.
     - `Abstract` – contains short summary of document.
     - `Introduction` – contains introductory information on context in which decision was raised. 
     - `Conventions` – contains conventional / glossary information used within document. 
     - `Decisions` – contains actual list of decisions with detailed reasons.
     - `Consequences` – contains results of decisions. During initial document publication this section is used as 
     a predefined section for future changes. As such, this section may only include `This section is currently empty.`
     or other placeholder to specify that no information is provided yet.
     - `Notes` – contains extra information. During initial document publication this section is used as
       a predefined section for future changes. As such, this section may only include 
       `This section is currently empty.` or other placeholder to specify that no information is provided yet.
     - `History of changes` – contains extra information on edits to this document. During initial document publication 
     this section is used as a predefined section for future changes. As such, this section may 
     only include `This section is currently empty.` or other placeholder to specify that no information 
     is provided yet. Formatting and typo changes may be omitted.
     In case of any meaningful changes made, this section MUST provide a list of entries with following information:
       - Date of change.
       - Short description of change / title.
       - Explanation on reasons on changes.
       - References to document sections with direct comparison of document text before / after changes.
     - `List of References` – contains a list of references on published papers and other materials, including
     websites, books, etc. This list is used to provide links to original documents that 
     were referenced withing document.
4. `ADRs` content files SHOULD follow this structure:
   - Within `Decision` section it is recommended to provide a list of decisions, each containing separate section per 
   decision with actual content of decision and reasons behind them. For example:
     - `Decisions`
       - `Decision 1`
         - `Contents`
         - `Reasons`
       - `Decision 2`
         - `Contents`
         - `Reasons`
